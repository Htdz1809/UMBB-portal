# Environment 2: Deploying on Render (PaaS)

This guide deploys the same application and PostgreSQL schema to Render. Render
manages the servers, networking, TLS and deployment pipeline; the team remains
responsible for the application, its configuration and its data.

## 1. Prerequisites

- A GitHub account and a repository containing this project. A private
  repository is fine.
- A Render account connected to GitHub.
- The project's `.env` file must **not** be committed. `.gitignore` excludes it.
- The administrator password chosen for the deployment.

Check the current Render plans and limits before selecting a plan:
<https://render.com/docs/free> and <https://render.com/pricing>. Limits quoted
below were checked in November 2026.

### Relevant free-plan limits

| Resource | Free plan limitation | Consequence for this project |
| --- | --- | --- |
| Web service | 512 MB RAM, 0.1 CPU | Sufficient for the assignment demonstration. |
| Web service availability | Spins down after 15 minutes without traffic; cold start about 1 minute | Warm the site before the video demonstration. |
| Free instance hours | 750 per workspace per month | Enough for one small service; exhausted hours suspend free services until the next month. |
| Web service filesystem | Ephemeral | The application must not store data on local disk; it uses PostgreSQL. |
| Free PostgreSQL | 1 GB storage, 100 connections, one free database per workspace | Adequate for sample data. |
| Free PostgreSQL lifetime | **Expires 30 days after creation**, with a 14-day upgrade grace period | Not suitable for permanent university data. Upgrade to a paid database (from about $6/month) for lasting persistence. |
| Free PostgreSQL backups | None | Take manual exports if the data matters. |
| Managed connection pooling | Not included on free | The app uses a small `pg` pool (maximum 10 connections). |

The 30-day database expiry is a plan limitation, not an application bug. For
the assignment, deploy close to the demonstration date; for real use, select a
paid Render Postgres plan.

## 2. Push the project to GitHub

From the project directory:

```bash
git init
git add .
git status
```

Confirm that `.env`, `node_modules/` and any real secrets are **not** staged.
Then:

```bash
git commit -m "Add UMBB university portal"
git branch -M main
git remote add origin https://github.com/<account>/<repository>.git
git push -u origin main
```

Alternatively create the repository in GitHub and use GitHub Desktop or
`gh repo create <name> --private --source=. --push`.

## 3. Deploy with the Blueprint (recommended)

`render.yaml` describes the web service, the database and the environment
variables.

1. Render Dashboard → **New +** → **Blueprint**.
2. Connect the GitHub repository and select the branch containing
   `render.yaml`.
3. Blueprint name: `umbb-portal`.
4. When prompted for `ADMIN_PASSWORD` (the variable uses `sync: false`), enter
   the administrator password. Render stores it as a secret.
5. Review the resources:
   - Web service `umbb-portal`, runtime Docker, plan Free, region
     Frankfurt, health check `/healthz`.
   - Database `umbb-db`, database `umbb`, user `umbb`,
     plan Free, region Frankfurt.
6. Click **Apply** / **Create resources**.
7. Wait for the database to become available and the web service image to build
   and deploy. The first build usually takes several minutes.

Important: keep the web service and the database in the **same region**. The
internal database URL is only reachable from the same region and workspace.
If Frankfurt is not appropriate, change `region` in `render.yaml` consistently
for both resources before applying.

### What the Blueprint configures

| Setting | Value |
| --- | --- |
| Web service name | `umbb-portal` |
| Runtime | Docker, `./Dockerfile` |

## 4. Manual deployment alternative

Use this if the Blueprint cannot be applied (for example, the workspace already
has a free database).

### 4.1 Create the database

1. Dashboard → **New +** → **Postgres**.
2. Name: `umbb-db`; database: `umbb`; user: `umbb`.
3. Region: the same region as the web service (Frankfurt).
4. Plan: Free (or a paid plan for persistence beyond 30 days).
5. Create the database and wait until it is available.
6. Open the database → **Connect** and copy the **Internal Database URL**. Use
   the external URL only for tools outside Render (it requires
   `?sslmode=require`).

### 4.2 Create the web service

1. Dashboard → **New +** → **Web Service**.
2. Connect the repository.
3. Name: `umbb-portal`.
4. Language/runtime: **Docker**. Dockerfile path: `./Dockerfile`.
5. Region: Frankfurt. Plan: Free.
6. Health check path: `/healthz`.
7. Add environment variables:

| Key | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `DATABASE_URL` | The database's **Internal Database URL** |
| `DATABASE_SSL` | `false` (internal URL); use `true` only if you deliberately connect through the external URL with TLS |
| `SESSION_SECRET` | A long random value, for example from `openssl rand -hex 48` |
| `ADMIN_USERNAME` | `admin` |
| `ADMIN_PASSWORD` | The administrator password (secret) |
| `COOKIE_SECURE` | `true` |
| `TRUST_PROXY` | `1` |

8. Create the web service. Render builds the Docker image and starts the
   container.

The application creates the schema and seed data automatically at startup. No
manual migration command is required.

## 5. Verify the deployment

1. Open the public URL, for example `https://umbb-portal.onrender.com`.
2. Check `/healthz`; it should return
   `{"status":"ok","database":"up"}`.
3. Open `/departments` and `/news`; seeded data should appear.
4. Sign in at `/admin/login` with the configured credentials.
5. Create an announcement, edit it, and check it on the public news page.
6. Delete a disposable announcement.
7. Optionally run the automated smoke test from the local machine:

```powershell
$env:ADMIN_PASSWORD = "the-render-admin-password"
npm run smoke -- https://umbb-portal.onrender.com --delete
```

The first request after idle may take about a minute while the free service
wakes up.

### Inspect the managed database

Render Dashboard → database → **Connect** → copy the **External Database URL**
and run:

```bash
psql "postgresql://<user>:<password>@<external-host>/<database>?sslmode=require" \
  -c "SELECT id, title, category, is_published FROM announcements ORDER BY id;"
```

You can also use the browser-based PSQL command shown in the dashboard. Never
put the external URL in the repository.

## 6. Demonstrate persistence

1. Add an announcement titled **Render persistence check** and note its ID.
2. In the Render Dashboard, open the web service and choose
   **Manual Deploy → Deploy latest commit** (or **Restart service**).
3. Wait for the deploy to finish and reload the public site.
4. The announcement must still be present.
5. Query the database with `psql` to show the row.

Explanation: the web service and database are separate managed resources. A
redeploy replaces the application container, but the data lives in Render's
managed PostgreSQL instance. The application also stores sessions in
PostgreSQL, so sessions can survive an application restart while the session
secret remains unchanged.

Do not confuse this with a persistent disk: the free web service filesystem is
ephemeral, which is why the design deliberately keeps all state in PostgreSQL.

## 9. Render-specific troubleshooting

- **Build cannot find `package-lock.json`:** commit the lock file; the
  Dockerfile runs `npm ci`.
- **Service exits immediately:** check logs for missing `SESSION_SECRET` or
  database connection errors. `NODE_ENV=production` requires a session secret.
- **Health check fails:** confirm the app listens on the port from `PORT`
  (Render injects it) and on `0.0.0.0`. The Dockerfile uses port 3000 and
  `server.js` binds to `0.0.0.0`.
- **`server does not support SSL connections`:** the internal URL does not need
  TLS. Set `DATABASE_SSL=false` for the internal URL. If using the external URL,
  set `DATABASE_SSL=true` and append `?sslmode=require`.
- **Login does not persist:** verify `TRUST_PROXY=1` and `COOKIE_SECURE=true` so
  the Secure cookie is accepted behind Render's HTTPS proxy.
- **Free database expired:** the 30-day limit was reached. Upgrade the database
  within the 14-day grace period; otherwise Render deletes it.
- **Slow first request:** free web services spin down after 15 minutes. Warm
  the site before demonstrating.
- **Free instance hours exhausted:** free services are suspended until the next
  calendar month. Check workspace usage.
