1. Qu'est-ce que Docker et pourquoi l'utiliser ?

Dans le développement logiciel traditionnel, un projet qui fonctionne sur l'ordinateur d'un développeur peut rencontrer des erreurs sur la machine d'un collègue ou sur le serveur de production. Cela est souvent causé par des versions différentes de Node.js, des bibliothèques manquantes, ou des configurations de base de données discordantes (le fameux problème "It works on my machine").

Docker résout ce problème fondamental par la conteneurisation :

  • Le Conteneur : C'est un environnement virtuel autonome, ultra-léger et étanche. Il contient tout ce dont l'application a besoin pour s'exécuter : le système d'exploitation minimal (Linux Alpine), la version exacte de Node.js (v22), les dépendances npm de production, le code source et les configurations.
  • L'Image Docker : C'est un "instantané" (snapshot) immuable et figé de votre application, construit une fois et exécutable à l'identique partout.
  • Le Dockerfile : C'est le fichier texte contenant la suite précise d'instructions permettant de fabriquer automatiquement cette image Docker.
Différence clé : Conteneur Docker vs Machine Virtuelle (VM)

Une Machine Virtuelle classique (comme sous VirtualBox ou VMware) virtualise un ordinateur complet avec son propre BIOS, son pilote matériel virtuel et un OS lourd de 5 à 15 Go qui consomme énormément de mémoire vive.

Un conteneur Docker, quant à lui, partage le noyau du système d'exploitation hôte. Il démarre en 1 à 2 secondes, ne pèse qu'une centaine de mégaoctets et consomme uniquement la RAM réellement requise par l'application (environ 40 Mo pour notre portail Node.js).

2. Le Code Intégral de notre Dockerfile

Voici le code exact du fichier Dockerfile présent à la racine de notre projet UMBB : 

01 FROM node:22-alpine AS dependencies
02 WORKDIR /app
03 COPY package.json package-lock.json ./
04 RUN npm ci --omit=dev
05 
06 FROM node:22-alpine AS runtime
07 ENV NODE_ENV=production
08 WORKDIR /app
09 
10 COPY --chown=node:node --from=dependencies /app/node_modules ./node_modules
11 COPY --chown=node:node package.json server.js ./
12 COPY --chown=node:node src ./src
13 COPY --chown=node:node db ./db
14 COPY --chown=node:node views ./views
15 COPY --chown=node:node public ./public
16 
17 USER node
18 EXPOSE 3000
19 
20 HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
21   CMD node -e "fetch('http://127.0.0.1:' + (process.env.PORT || 3000) + '/healthz').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"
22 
23 CMD ["node", "server.js"]

3. Explication Détaillée Ligne par Ligne du Dockerfile

Ce Dockerfile utilise la technique professionnelle du Multi-stage build (construction en plusieurs étapes). Il se décompose en deux phases distinctes : l'étape de préparation des dépendances (dependencies) et l'étape d'exécution finale (runtime).

ÉTAPE 1 : INSTALLATION DES DÉPENDANCES

Lignes 1 à 4 : Construction de la couche des modules

  • FROM node:22-alpine AS dependencies (Ligne 1) :
    Définit l'image de base. Nous utilisons Node.js 22 LTS basé sur la distribution Alpine Linux. Alpine est un système Linux minimaliste et ultra-sécurisé dont la taille de base ne dépasse pas 5 Mo, éliminant tout paquet inutile ou vulnérable. Le mot-clé AS dependencies donne un nom à cette première étape pour pouvoir y faire référence plus tard.
  • WORKDIR /app (Ligne 2) :
    Définit le répertoire de travail dans le conteneur. Toutes les commandes suivantes seront exécutées depuis le dossier /app.
  • COPY package.json package-lock.json ./ (Ligne 3) :
    Copie uniquement les manifestes de dépendances dans le conteneur.
    Principe d'optimisation (Docker Layer Caching) : Docker met en cache chaque ligne. En ne copiant que ces deux fichiers avant de lancer l'installation, Docker évite de réinstaller tous les paquets npm si vous modifiez seulement une vue HTML ou du CSS !
  • RUN npm ci --omit=dev (Ligne 4) :
    Installe de manière stricte et déterministe les dépendances définies dans package-lock.json. L'option --omit=dev garantit qu'aucun outil de développement (comme supertest) n'est installé, ce qui réduit considérablement le poids final.
ÉTAPE 2 : ENVIRONNEMENT D'EXÉCUTION FINAL

Lignes 6 à 9 : Initialisation de l'image de production

  • FROM node:22-alpine AS runtime (Ligne 6) :
    On repart d'une image Alpine vierge. Les outils temporaires d'installation npm ne seront pas conservés dans cette image finale, ce qui protège le code et allège l'image.
  • ENV NODE_ENV=production (Ligne 7) :
    Déclare la variable d'environnement de production. Dans Express.js et EJS, cela active automatiquement la mise en cache des vues compilées en mémoire et désactive les traces de débogage verbeuses.
  • WORKDIR /app (Ligne 8) :
    Crée et cible le répertoire de travail de production.

Lignes 10 à 15 : Transfert sécurisé du code source

  • COPY --chown=node:node --from=dependencies /app/node_modules ./node_modules (Ligne 10) :
    Récupère le dossier node_modules calculé lors de l'étape 1 (--from=dependencies).
    L'option de sécurité --chown=node:node : Attribue immédiatement la propriété des fichiers à l'utilisateur système standard node plutôt qu'au super-utilisateur root.
  • COPY --chown=node:node ... (Lignes 11 à 15) :
    Copie les fichiers nécessaires au fonctionnement de l'application :
    • server.js et package.json : Le point d'entrée HTTP.
    • src/ : L'architecture MVC (routes publiques, routes admin, middlewares, sécurité).
    • db/ : Les scripts de création de tables (schema.sql) et de données (seed.sql).
    • views/ : Les templates HTML / EJS du portail.
    • public/ : Les fichiers statiques (CSS, images des logos des facultés, vidéo institutionnelle pres.mp4, JavaScript client).

Lignes 17 à 23 : Droits d'accès, Ports, Healthcheck et Démarrage

  • USER node (Ligne 17) :
    Règle d'or de la cybersécurité (Moindre Privilège) : Par défaut, un conteneur s'exécute en tant que root. Si une faille était découverte dans un paquet, un attaquant pourrait tenter de s'échapper du conteneur. En basculant vers l'utilisateur sans privilèges node, le conteneur n'a aucun droit administratif sur la machine hôte.
  • EXPOSE 3000 (Ligne 18) :
    Documente que l'application écoute sur le port réseau interne 3000.
  • HEALTHCHECK ... (Lignes 20-21) :
    Indique à Docker comment vérifier que le site fonctionne réellement :
    • --interval=30s : Effectue un test toutes les 30 secondes.
    • --timeout=5s : Échoue si le serveur ne répond pas en 5 secondes.
    • --start-period=20s : Laisse 20 secondes au serveur pour démarrer avant d'alerter.
    • --retries=3 : Déclare le conteneur unhealthy après 3 échecs consécutifs.
    • La commande exécute fetch('http://127.0.0.1:3000/healthz') pour valider que la base PostgreSQL et le serveur Express sont opérationnels.
  • CMD ["node", "server.js"] (Ligne 23) :
    La commande exécutée automatiquement au démarrage du conteneur.

4. Comment le Dockerfile s'intègre avec Docker Compose

Le Dockerfile gère l'application Node.js, mais notre portail a aussi besoin d'une base de données PostgreSQL. C'est ici qu'intervient docker-compose.yml pour orchestrer les deux services ensemble.

Service Origine de l'image Réseau Fonction dans le projet
app (Site Web) Construite via notre Dockerfile Port 3000 exposé sur l'hôte Traite les requêtes HTTP, génère les pages EJS, gère les sessions et uploads.
db (PostgreSQL) Image officielle postgres:16-alpine Réseau privé backend (Port 5432) Stocke les facultés, annonces et sessions de façon isolée et sécurisée.
Points d'Architecture Clés dans docker-compose.yml
  1. Réseau Privé Isolé : La base de données PostgreSQL n'a aucune ligne ports:. Cela signifie qu'elle est totalement inaccessible depuis Internet et ne répond qu'au conteneur app via l'adresse interne db:5432.
  2. Persistance des Données (Volume pgdata) : Les données de la base ne sont pas stockées dans le conteneur mais dans un volume Docker sur le disque hôte. Lorsque vous arrêtez ou reconstruisez les conteneurs, aucune donnée n'est perdue.
  3. Démarrage Ordonné (depends_on) : Grâce à la directive condition: service_healthy, l'application Express attend que PostgreSQL ait fini son initialisation et réponde à pg_isready avant de démarrer.

5. Procédure Pas à Pas pour Lancer le Projet sur un Autre PC

Grâce à cette configuration Docker, faire tourner l'intégralité du projet sur un tout nouvel ordinateur (Windows, Mac ou Linux) ne nécessite que 3 commandes :

Étape 1 : Récupérer le code source

git clone https://github.com/Htdz1809/UMBB-portal.git
cd UMBB-portal

Étape 2 : Créer le fichier d'environnement .env

Copiez le modèle préconfiguré .env.example vers .env :

# Sur Windows (PowerShell) :
Copy-Item .env.example .env

# Sur Linux / macOS / Git Bash :
cp .env.example .env

Étape 3 : Lancer la construction et l'exécution

docker compose up -d --build

Docker va alors automatiquement :

  1. Télécharger l'image de PostgreSQL 16 Alpine.
  2. Lire le Dockerfile et construire l'image de l'application Node.js.
  3. Créer le réseau privé et le volume de stockage.
  4. Initialiser les tables et insérer les 8 facultés/instituts UMBB en anglais ainsi que les annonces de démonstration.

Accès aux interfaces :

  • Portail Étudiants & Public : http://localhost:3000
  • Tableau de Bord Administrateur : http://localhost:3000/admin/login
  • Identifiant : admin / Mot de passe : ChangeMe-Administrator-2026!

6. Tableau Récapitulatif des Commandes Docker Utiles

Action Commande Description
Démarrer docker compose up -d --build Reconstruit l'image avec les derniers changements et lance les conteneurs en arrière-plan.
Vérifier docker compose ps Affiche l'état des conteneurs (vérifie s'ils sont Up (healthy)).
Voir les logs docker compose logs -f app Affiche les messages du serveur Express et les erreurs en direct.
Arrêter docker compose down Arrête les conteneurs proprement sans supprimer les données du volume PostgreSQL.
Réinitialiser docker compose down -v Arrête les conteneurs et supprime le volume de données (remet la base à neuf).
Conclusion Technique

L'association d'un Dockerfile Multi-Stage et d'un orchestrateur Docker Compose offre une isolation totale, une sécurité renforcée (utilisateur non-root, réseau interne privé), une empreinte mémoire minimale (~150 Mo), et une portabilité absolue garantissant une exécution identique en local ou sur n'importe quel serveur Cloud.
